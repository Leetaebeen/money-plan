# 커밋 메시지 규칙

모든 일반 커밋은 변경 목적을 한 가지로 제한하고 아래 형식을 사용합니다.

```text
<type>(선택 scope): 한 줄 요약

- 변경한 핵심 내용
  - 필요한 경우 세부 내용
- 동작이나 정책이 어떻게 달라졌는지
- 추가한 테스트 또는 보안 조치
```

## 허용 타입

- `feat`: 새 기능
- `fix`: 버그 수정
- `security`: 보안 강화
- `refactor`: 사용자 동작을 바꾸지 않는 구조 개선
- `perf`: 성능 개선
- `test`: 테스트 추가 또는 수정
- `docs`: 문서 변경
- `build`: 빌드 또는 의존성 변경
- `ci`: CI/CD 변경
- `chore`: 설정 및 유지보수
- `style`: 코드 의미를 바꾸지 않는 형식 변경

제목 다음에는 빈 줄 하나가 필요합니다. 본문에는 최상위 `- ` 항목이 최소
하나 있어야 하며, 하위 항목은 단계마다 공백 두 칸을 사용합니다. 일반 설명
문장은 쓰지 않고 모든 본문 내용을 목록으로 기록합니다.

`feat`와 `fix`처럼 독립적으로 되돌릴 수 있는 변경은 별도 커밋으로 나눕니다.
Git이 자동 생성한 merge 및 revert 메시지만 형식 검사에서 제외합니다.

## 예시

```text
feat: 시장별 워크포워드 학습 모델 진입 필터 연결

- 국장과 미장 학습 데이터를 분리해 시장별 모델 파일 생성
- 최초 60% 기간 이후 3개 구간을 순차 검증
  - 검증 구간 중 최소 2개가 비용 차감 후 양수일 때만 승인
- 승인된 모델만 신규 진입 필터에 적용
- 시장 분리와 런타임 차단 회귀 테스트 추가
```

저장소를 처음 복제한 뒤 `npm run setup:git`을 한 번 실행하면 로컬 커밋 훅과
메시지 템플릿이 활성화됩니다. GitHub Actions에서도 같은 규칙을 다시 검사하므로
`--no-verify`로 로컬 훅을 우회한 커밋도 기본 브랜치 검증을 통과할 수 없습니다.
